Under the hood

How it works

One app, one repo, one Firebase project. A one-day summit app was extended, a module at a time, into a year-round network platform without rewriting or breaking any of it. The network is the umbrella, and the summit is one event inside it.

Architecture: a modular monolith, no build step

Front end

One app shell + ES modules

Native browser modules for auth, events, community, and the XP game. Static files on Firebase Hosting, installable as a PWA.

Identity

Google sign-in or a magic link

Firebase Auth. The email's domain decides the track, which decides how fast a person gets reviewed.

Data

Firestore + least-privilege rules

Members, meetings, domains, ledger, roles. The rules enforce every gate the pages display.

Messaging

Transactional email

Confirmation, approval, and decision emails. Each one prefers the member's chosen contact address.

The rules that carry the weight (trimmed, simplified)

// A member can edit their profile, but never their own status.
// "pending" is the waitlist; only staff can flip it to "active".
match /networkMembers/{uid} {
  allow create: if request.auth.uid == uid
    && request.resource.data.status == 'pending';
  allow update: if isStaff()
    || (request.auth.uid == uid
        && request.resource.data.diff(resource.data).affectedKeys()
             .hasOnly(['bio', 'contactEmail', 'photo']));
}

// XP: one doc per member, per month, per vector. The ID is the rule.
match /xpLedger/{id} {
  allow create: if id == request.auth.uid + '_' + thisMonth() + '_' + request.resource.data.vector;
  allow update: if false;   // a second ATTEND this month can't land
}

// Owners are hardcoded as a lockout safeguard: if the roles
// collection is ever emptied, these accounts can still get back in.
function isStaff() { return isOwner() || hasRole(['admin', 'coordinator']); }

Design decisions worth explaining

1

Two emails per person

Districts often put staff mail on one system and Google Workspace on a second domain, and Google sign-in presents the second one. So both domain types live in the seed, and every automatic email goes to the member's "best contact" address first. When someone says they never got the email, that's the first thing to check.

2

Track is recomputed at render time

A track stamped at sign-up goes stale when a domain is added later. Recomputing from the email means district staff never sit in the guest queue forever. They show up with a "reclassified" pill, and approving them writes the corrected track.

3

The system learns, carefully

Approving a self-declared applicant teaches their domain, so the next colleague is auto-verified. Gmail and other personal providers can never be learned, and partner or guest trust is never applied to a whole domain. Recategorizing a domain never touches active members.

4

XP without counters

Level is the count of ledger docs, computed from the ledger and never from a cached field the member could write. That leaves no drift, no race conditions, and no replays.

5

Public topics, gated logistics

Topics are the reason people register, so everyone sees them. Times, rooms, and calendar invites unlock after approval, and approved guests unlock only their one meeting.

6

Built for a three-person team

Approvals, meetings, room codes, and exports all happen in the admin UI, so co-admins can run the network without touching code or git.
